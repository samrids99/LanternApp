# ADR 010: Endpoint structure

- **Status:** Accepted
- **Date:** 2026-11-19

## Context

The next phase is to create the first endpoint for the GET / Regions request. The decision to be made was to choose where and how this logic will be placed

Two approaches were considered:

- **RegionsController.** The api uses controller classes to receive and handle HTTP requests. This is what I am familiar with given it is what I use in my job.
- **A minimlal API** The new Microsoft default structure. Grouped by feature in static endpoint classes, each with a map...endpoints extension called from program.cs

## Decision
1. **Use the Minimal API approach.**
where endpoints live (Lantern.Api/Endpoints/)
one static class per feature, with a Map...Endpoints extension called from Program.cs
MapGroup for the path prefix

## Consequences
**Drawbacks**
- Unfamiliar territory and will take adjustment to a new way of doing things.
- Seems less clear and intuitive at first glance.
- Controllers are tidy by design, minimal api approach will require me to be on top of keeping code neat.

**Benefits**

- Less ceremony. There’s no base class, [Route] and [HttpGet] attributes, or constructor wiring up fields.
- Each endpoint declares only what it needs. A controller’s constructor collects every dependency for every action. A handler lists its own.
- The current default way of doing things is to use a minimal api.
- Boosts my knowledge and employability by developing a new skillset and understanding.
