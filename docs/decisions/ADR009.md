# ADR 009: Region seeding behaviour

- **Status:** Accepted
- **Date:** 2026-11-13

## Context

Stays will point at a region (ADR 001, ADR 006), so the list of regions has to be in the database before any stay can be created, and it will change over time as new areas are added or corrected. Regions are never created by users, and stays will store region IDs, so those IDs must stay stable.

Several approaches were considered:

- **`HasData` in the EF configuration.** The seed becomes part of the migrations, so it is versioned with the schema. The cost is that every change to the region list needs a new migration.
- **A seeder that reads `regions.json`.** The file stays the single source of truth and data changes need no migration. The cost is that the seeder has to be written carefully: it must be safe to run repeatedly and must respect the foreign key between a region and its parent.
- **Insert-only versus update on difference.** Insert-only is simpler, but once a region exists the file can no longer correct it, so the file stops being the source of truth.
- **Deleting regions removed from the file versus keeping them.** Deleting keeps the database tidy, but would orphan any stay that references the region.
- **Keeping the file in parent-first order versus sorting in code.** A convention costs nothing to write but nothing enforces it, so a mistake only shows up as a foreign key error at insert time.
- **Seeding in every environment, in Development only, or as a separate deployment step.** Seeding at every startup is convenient, but two instances starting at once could race on the primary key, and a bad file would stop the app.

## Decision

1. **`regions.json` is the single source of truth, read by a seeder (`RegionSeeder`), not by `HasData`.** This avoids a new migration for every region change, and keeps the data in a file that can be reviewed in a pull request.
2. **The seeder inserts missing regions and updates existing ones whose values differ.** Existing rows are loaded tracked, so EF compares the original values with the file's and writes only the columns that changed. A second run with unchanged data writes nothing. This lets a region be corrected in the file without reversing the source-of-truth decision.
3. **The seeder never deletes a region.** Stays will reference region IDs, so removing a row would orphan them. If the database holds IDs that are not in the file, the seeder logs a warning and leaves them untouched.
4. **Regions are sorted by depth before insert.** Parents are always handled before children, so the order of rows in the file does not matter and there is no ordering rule to forget. A missing parent or a parent loop throws, naming the region.
5. **Seeding runs in Development only, at startup.** There is one developer and one instance, so the race condition does not apply yet. Seeding in production is deferred until deployment is designed.

## Consequences

**Benefits**

- Changing, adding or correcting a region means editing one file, with no migration.
- The seeder is idempotent, so it is safe to run on every startup in Development.
- Row order in the file is irrelevant.
- Drift between the file and the database is visible in the log instead of silent.

**Costs and known gaps**

- The file is authoritative, so a typo overwrites good data on the next run. The seed validation tests matter more because of this.
- Removing a region from the file does not remove it from the app, because rows are never deleted. There is no way to retire a region yet. A `retired` flag is my likely choice.
- Removing a parent from the file while leaving its children makes the seeder throw, even though the parent still exists in the database.
- Changing a region's parent or type affects roll-ups for stays that already point at it.
- A foreign key problem or a bad file now stops application startup in Development.
- Seeding in production is undecided. At startup it would need protection against two instances racing, or it should become a separate deployment step.
- The depth sort and the update path are currently verified by hand only. Integration tests against a real Postgres container (empty database, seed twice, changed value, reversed input, region missing from the file, parent links intact) are still to be written.
