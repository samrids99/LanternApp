# ADR 011: JSON conventions on the wire

- **Status:** Accepted
- **Date:** 2026-11-23

## Context

`GET /regions` returns `RegionDto`, which includes the `RegionType` enum. By default,
System.Text.Json writes enums as numbers, so `Locality` would appear as `3`. The typed
TS client planned in ADR 003 is generated from the OpenAPI document, so what the
document says and what the API actually sends both have to be right.

Two things came up while building the first endpoint:

- The enum would reach clients as an opaque number, and the number depends on the
  order of the members in the C# enum.
- The OpenAPI document typed `id` and the coordinates as `integer` **or** `string`.
  ASP.NET Core's default JSON settings allow reading numbers from strings, and the
  document mirrored that. A generated client would have typed `id` as `number | string`.

## Decision

1. **Serialise enums as their names**, using `JsonStringEnumConverter`, registered once
   in `ConfigureHttpJsonOptions` in `Program.cs`.
2. **Use strict number handling** (`JsonNumberHandling.Strict`) in the same place.

Both settings live in the Api layer. The Domain has no JSON attributes and doesn't
know how it is serialised.

### Alternatives considered

- **Leave enums as numbers (the default).** Compact, but opaque to anyone reading a
  response, and fragile if members are reordered.
- **`[JsonConverter]` on the enum in the Domain.** Works, but couples the Domain
  to System.Text.Json for a presentation concern.
- **Leave `NumberHandling` at its default.** Works at runtime, but gives a looser
  contract than the API actually honours.

## Consequences

**Benefits**
- Responses are readable: `"type": "Locality"`.
- The OpenAPI document matches the real responses: `RegionType` is listed as
  `Country`, `Area`, `Locality`, and `id` is a plain `integer`.
- One place to change, and every future endpoint inherits it.

**Drawbacks**
- The enum member names are now part of the API contract. **Renaming or removing a
  `RegionType` member is a breaking change** for any client. Adding one is additive,
  but clients with an exhaustive switch need to handle it.
- Strict number handling also applies to requests, so a number sent as a string
  (`"3"`) will be rejected once an endpoint takes a body.
- Payloads are slightly larger than with numbers.

## Evidence and tests

- `curl /regions` returned `"type":"Locality"`, and `/openapi/v1.json` listed the enum
  names. After the change, `id` appeared as `integer`.
- `Api/RegionEndpointsTests` fails if the enum stops being a string, or if
  `parentRegionId` stops being present as `null`/number. I confirmed each by removing
  the converter and by setting `WhenWritingNull`.
- **Not covered:** nothing tests `NumberHandling.Strict` yet. `GET /regions` doesn't read
  a body, and OpenAPI isn't mapped in the `Testing` environment. Revisit when the first
  endpoint that accepts JSON exists.
